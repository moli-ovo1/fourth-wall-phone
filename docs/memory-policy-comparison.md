# Memory Policy v1 参数对照

已采用用户批准的20轮默认，10轮保留实验覆盖；阈值定义在Policy，Engine状态机没有20轮字面量。

## 默认值

| 字段 | 普通Conversation | Fourth-wall |
|---|---|---|
| active | 目标50完整轮，正常40–60调节 | 所有未有效归档原文，弹性长窗口 |
| 自动整理 | eligible≥20轮 OR ≥4k Token | 整包≥128k Token |
| 无tokenizer | eligible≥6k字符 | 不接受缺失整包Token计数 |
| active压力 | 软12k/硬16k Token，受已知availableTokens约束 | 158k整包上限，受模型可用预算约束 |
| ordinary batch | 8k Token或12k字符原文批次；实际provider提示还需预算 | 使用皮下Policy和未来provider的实际请求预算 |
| dirty | 绕过正常压缩门槛修复 | 同样，不等128k |

## 单位与模拟

一用户消息+两个角色气泡为3条消息/完整轮。40/50/60/100轮分别约120/150/180/300条；1或3角色气泡时范围是2–4条/轮，用户多条还会增加条数。测试覆盖1/3/6/12气泡、连续用户输入、空输入继续、legacy推断、commentary和失败。

固定active=50、无体量压力、每批一次成功调用、不计长期合并/重试/修复：

| trigger | 首次总完成轮数 | 每100新增eligible轮基础调用 |
|---|---:|---:|
| 10 | 60 | 10 |
| **20** | **70** | **5** |
| 40 | 90 | 2.5 |
| 60 | 110 | 1.67 |
| 100 | 150 | 1 |

自动测试不仅断言公式：对10/20配置依次追加到150个完整轮次、提交每次计划batch的覆盖ID，实际观察到10/5次整理计划。它不是收费API实测。

测试还交叉active=40/50/60/100与trigger=10/20/40/60/100，并测试长内容1轮eligible达到4k即可提前触发。测试的100轮active必须显式调整normalMax，不能无意绕过配置校验。

20轮等待区可能有19轮过渡原文，因此实际原文50+19=69轮只是低体量、未整理成功前的上界之一，不能继续套用10轮方案的59轮描述。桥接与active共同受请求预算保护，超限返回mustWaitBeforeSend；不得提前推进覆盖或把未摘要内容悄悄丢弃。

若20轮增加连续性损失，应先比较摘要信息保留、真实Tokens、基础与重建API成本再调整；该批只有确定性合成测试，没有用户真实聊天采样和LLM质量测评。

## 保持与改变

普通旧设置recentChatLimit仍表示消息条数；引擎提供legacy-messages模式，未修改任何现有设置。长期合并按800/500去重源轮次提供计划，防止20轮小摘要使旧8段/5段逻辑提前五倍。

Fourth-wall非超限时全部未归档原文可读；保持原保护约5段完成交流/10条消息/pending规则，不采用普通50轮。新稳定覆盖参数支持消息删除或排列变化；旧archivedCount没有版本证明时只报blocked，不冒充精确覆盖。

以上行为仅在独立模块中通过测试。生产仍使用原逻辑，等待受保护文件交接后才可以形成完整读取、修改与提交闭环。
